# Changelog

## v1.0.0 (unreleased)

tinyns v1 is a rewrite: a new full-JAX core, a new algorithm and a new API.
**It is a hard break from v0.x.** There are no compatibility shims, no
deprecated aliases and no readers for v0.x checkpoints or result files; no
result is bit-identical to v0.x. Finish in-flight runs on the version they
started on. The per-PR development notes that this entry replaces are in the
git history of this file (up to commit eb4631c).

### Highlights

- **The whole run executes on the device.** A compiled `lax.while_loop` runs chunks of steps on the GPU or CPU; the host syncs once per chunk.
- **Speed.** On one NVIDIA H100 in float32, a 13-D correlated Gaussian with 1000 live points runs to `dlogz = 0.1` in 0.93 s once compiled and 9.8 s on a first run (about 8 s of it compilation), against 47 s and 53 s for v0.2.5: 50x compiled, 5x with compilation. At 4000 live points it is 1.15 s (10.3 s) against 227 s (233 s): 200x and 23x. With `num_delete=1` v1 takes 35 s and 136 s compiled, 1.3x and 1.7x faster than v0.2.5. A two-mode 10-D target took 0.91 s compiled against 0.66 s for a 10-D Gaussian (15 to 20% more time per likelihood call with clustering and hops active). Measured on the final v1 core (d638c55), which is slower than the first v1 core (0.56 s on the same target) because of the mode tracking. For a cheap likelihood the run time on a GPU is nearly flat in `nlive`, because the number of steps does not depend on `nlive` when `num_delete` is proportional to it.
- **Multimodal posteriors are handled inside the sampler.** An exact inter-mode move cut the seed-to-seed scatter of minor-mode weights about 7x against chains seeded from live points alone, at the same number of likelihood calls (v1 bake-off: Gaussian mixtures of two and three modes in 4 to 32 dimensions, 40 seeds per cell, H100).
- **Batched runs.** `run(keys)` runs a batch of independent runs in one compiled program; with `batched_data=True` each run has its own dataset (SBC and mock campaigns compile once).
- **Checkpoints.** `run(key, checkpoint=path)` writes and auto-resumes; a resumed run is bit-identical to an uninterrupted one.
- **A functional core** (`Config`, `init`, `step`, `finalise`) next to the `NestedSampler` class.

### Algorithm

- **Step.** Each step deletes the `k = num_delete` lowest live points and replaces them with the end points of `k` fixed-length Metropolis chains, vmapped. A chain is seeded from a live point above the new contour `L*`; proposals outside the unit cube or at or below `L*` are rejected (no reflection), and a chain that never moves returns its seed (no retry rule). With `num_delete=1` the chain is not vmapped, so an out-of-cube proposal skips the likelihood call.
- **On-device clustering** (`tinyns/modes.py`). Every quarter e-fold of prior volume the live points are reclustered in 8 fixed slots: warm-started hard EM, merges, and top-down Fisher splits. Every cluster has an id: the two parts of a split take new ids and the id they were split from is recorded as their parent, so an id names one cluster from the split that made it to the split that ends it (a merge keeps the id of the cluster that absorbs the other).
- **Local random walk.** A walk step is `x + s L_c z`, with `L_c` the Cholesky factor of the covariance of the cluster of `x`, and the exact Hastings ratio when the proposal lands in another cluster. With one cluster it is a walk in the live-point covariance. The scale `s` adapts toward 25% acceptance after every step.
- **Hop.** Every 10th chain step is an independence Metropolis-Hastings proposal from the uniform law on the union of the clusters' ellipsoids (the bake-off arm `B_ell`), accepted with the ratio of proposal densities. With fewer than two eligible clusters it is a walk step.
- **Cross-fitting.** The live slots form three folds. A new point is seeded from the fold of the slot it fills, and its chain's clusters and covariances are fitted to the other two folds only. The kernel therefore does not depend on the seed or its ancestors, and it leaves the uniform law on `{L > L*}` invariant for any chain length. `modes.py` gives the argument.
- **Default `walks`** is `max(25, 6 * ndim, ndim**2 // 6)` (`tinyns.core.default_walks`). It keeps the logZ bias below its scatter on correlated Gaussians from 2 to 64 dimensions with 250 to 2000 live points.
- **Evidence.** The `k` deaths of a step are counted at live counts `m, ..., m-k+1` (birth/death contours; Fowlie, Handley & Su) and the final live points at `m, ..., 1`. `finalise` recomputes the weights, `logz` and `logzerr = sqrt(sum_i dH_i / n_i)` on the host in float64. `result.nlive_i` holds the live count at every death.
- **Termination.** The run stops when `log(Z + X max L_live) - log Z < dlogz`, at `maxiter` dead points, at `maxcall` likelihood calls, or on a likelihood plateau (no live point above the deleted ones).

### API

- **Sampler.** `NestedSampler(loglike, prior_transform, ndim, nlive=1000, *, num_delete=None, walks=None)`, with `num_delete` defaulting to `max(1, nlive // 10)` (at most `nlive // 2`). `loglike` and `prior_transform` are JAX-traceable functions of one point. Unknown keywords raise `TypeError`.
- **Run.** `sampler.run(key, *, dlogz=0.1, maxiter=None, maxcall=None, progress=False, checkpoint=None, batched_data=False)`. `key` is a PRNG key (typed or raw), an int seed, or a batch of keys. `progress=True` prints one line per chunk.
- **Int seeds.** Every public function that takes a key takes an int seed too: `run`, `init`, `result.resample_equal` and `tinyns.math.systematic_resample`.
- **Functional core.** `Config(ndim, nlive, num_delete, walks)`, `init(key, loglike, prior_transform, cfg)`, `step(state, loglike, prior_transform, cfg) -> (state, dead)` and `finalise(state, dead, cfg, prior_transform=..., dlogz=..., ncall=...)`. `State` and `Dead` are pytrees of arrays. `tinyns.core` also has `default_walks` and the integer status codes.
- **Hand-written loops.** `tinyns.delta_logz(state, cfg)` is the stopping statistic of `run`, and `tinyns.STATUS` names the status codes (`STATUS[int(state.status)]`). `step` does not test termination, so `finalise(..., dlogz=)` applies the rule of `run`: a running state with `delta_logz < dlogz` is reported as converged (`success=True`); without `dlogz` the result says `running`. `State.ncall` is an int32, which wraps after `2**31` likelihood calls: `run` drains it, and a long hand-written loop adds up its increments on the host and passes `finalise(..., ncall=)`, as `examples/functional_core.py` does.
- **Exports:** `NestedSampler`, `Config`, `init`, `step`, `finalise`, `delta_logz`, `STATUS`, `NestedSamplingResult`, `LogZBootstrap`.
- **Result.** Fields: `samples`, `samples_u`, `logl`, `logwt`, `logl_birth`, `nlive_i`, `labels` (the id of each sample's cluster when it died, as `id * folds + clustering`), `logz`, `logzerr`, `ncall`, `niter`, `nlive`, `num_delete`, `ndim`, `success`, `message`, `metadata`. Methods: `summary()`, `diagnostics()`, `weights()`, `resample_equal()`, `modes()`, `insertion_indices()`, `insertion_test()`, `logz_bootstrap()`, `information()`, `save_npz()`/`load_npz()` (format `tinyns-result-npz-v3`), `to_dict()` and `to_numpy()` (every field, `labels` included), `to_dynesty_dict()`.
- **`result.modes()`** reads the cluster labels the run recorded and returns each mode's mass, its seed-to-seed scatter (`urn_sd`; an upper bound for a mode the hop balanced), its smallest live count, an `unresolved` flag (fewer than `5 * ndim` live points) and a `tracked` flag (`False`: the sampler's clustering did not separate the mode, see below). `summary()` prints the table when there is more than one mode, and `diagnostics()` adds a warning per unresolved mode.
  - *Counting.* Labels that touch are merged (a gap of less than 3 within-cluster standard deviations along their discriminant, at one of their posterior medians). Three kinds of label do not merge the modes they touch: a cluster whose parts ended up apart (the recorded parents say which clusters were split into which), a cluster of another clustering that covers two modes (its own live points leave a gap between them), and an early cluster, which has no live points left at the median of the labels it touches (modes that are separate in the posterior bulk are still connected at a low likelihood contour). Before this, a cluster kept its label when it was split, so the label of a cluster that was split in the posterior bulk held several modes and merged them all: on the 10-D LogGamma target (4 modes of mass 1/4) 1 of 64 runs reported 4 modes at nlive 1000 and none at nlive 500, although the samples had all four with the right masses; now 64 and 63 of 64 do.
  - *Modes the clustering does not separate.* A mode is also cut wherever its live points leave a slab across a coordinate axis of the unit cube empty (width times the density of the 8 neighbouring points at least 30; the largest value over 768 runs of unimodal targets was 21.5). The modes this finds are `tracked: False`: the hop did not balance them, their masses scatter by about `urn_sd`, and their number is a lower bound. On the eggbox (18 modes, on a lattice that no two-way split separates) `modes()` reported one mode and no warning; it now reports 15 to 18 at nlive 1000, none tracked, with `urn_sd` of 0.40 and 0.57 for the modes of mass 0.08 and 0.04, whose masses scatter by 0.38 and 0.61 in logit over 64 seeds.
  - *Full slots.* `diagnostics()["mode_slots_full"]` is the fraction of the run during which all 8 cluster slots were in use. With more than one mode found it is a warning: no further mode could be split off then. It says that there may be more modes only when the clustering held no more clusters than the modes found; with more, the slots held pieces of the modes found (on an 18-D posterior with 2 modes the slots were full with 8 clusters, and the old warning was a false alarm).
  - *Within-run scatter.* Each mode has `fold_mass`, its mass among the samples of each of the three cross-fitted folds (a sample's fold follows from its label), and `fold_sd`, the standard deviation of its logit over the folds. A point and its descendants stay in one fold, so the folds sample the modes like three runs, and the run's mass scatters from run to run by about `fold_sd / sqrt(3)`: 0.024 against a measured 0.019 on a plain two-mode mixture in 18-D, 0.06 against 0.06 on `sepW_d10` and `sepW_d18`, 0.24 against 0.19 on `needle_d18`, 0.15 against 0.32 on `cauchy_d18` and 0.6 against 0.25 (3 runs) on an 18-D posterior with a funnel neck. `summary()` prints it.
  - *The hop's record.* A warning says when the hop balanced the modes only in part, from what the run recorded after the modes separated: the clustering held 1.5 clusters per mode or more on average over the posterior mass (`diagnostics()["mode_lumps"]`; at most 1.29 on the Gaussian mixtures, LogGamma and plain two-mode targets, 1.54 to 3.7 on the needle and Cauchy targets and on the 18-D posterior), the hop was off (fewer than two eligible clusters) for half of that mass or more (`mode_hop_off`), or it accepted less than 2% of its proposals (`hop_acceptance`; 0.6 to 0.8% on the 18-D posterior, at least 19% on every target of `bench`). The warning quotes each mode's `fold_mass` and `fold_sd`. It fired in all 16 runs of `needle_d18`, in all 14 runs of `cauchy_d18` that found both modes and in the 3 runs of the 18-D posterior, and in none of 64 runs of the Gaussian mixtures and plain two-mode targets; it fired in 2 of 8 `loggamma_d10` runs, where the hop was off for 0.55 and 0.82 of the mass but the folds agreed within 0.17.
  - *`tracked`.* A mode that the empty-slab pass cut out is still `tracked` if at least half of its posterior mass carries labels that put 90% of their mass in it: the clustering separated it, and only the merging of labels had failed. The warning that modes "were not separated by the sampler's clustering" was wrong for both modes of one run of the 18-D posterior.
  - *Lumps of a mode.* A sixth pass merges two modes when the likelihood dips by less than 3 between them: along their discriminant direction, the highest likelihood of their samples in 16 bins between their medians. Lumps that the clustering cut off a mode with thin arms leave gaps in the live points like separate modes, but their dead points show no saddle (dips of 0.0 to 1.8 on `needle_d18` and an 18-D posterior with a funnel neck, against at least 5.7 between the modes of LogGamma and 40 to 200 on the mixtures, the Cauchy target and the eggbox). On the 18-D posterior this removed the spurious third mode of one run and two of the three spurious modes of another; the third, a funnel neck that joins its mode only along a curved path, remains (flagged unresolved).
  - *Unimodal targets.* One mode in 255 of 256 runs of the 5-D and 10-D bananas (nlive 500 and 1000), the second mode of the other run flagged unresolved; in all 64 of each of the Gaussians (2-D, 10-D), the funnel and the 4-D Rosenbrock. A mode found by one clustering only is dropped if no live point of another fold lies among its points (the descendants of a stuck chain stay in one fold), and a small mode is merged into another if the live points of the labels left out fill the gap between them.
  - *The 10-D Rosenbrock is not unimodal.* It has a second lobe at `x_1 = -1` with 2.52% of the posterior mass (quadrature), joined to the main mode by a bridge that holds 0.8%. At nlive 1000 the lobe holds about 25 live points, under `5 * ndim`, so the runs that report it (7 of 64) mostly flag it unresolved, and they are right to.
- **`result.insertion_test()`** ranks each new point among the `nlive - num_delete` survivors of its step and tests the ranks for uniformity, pooled and in windows.
- **`result.metadata` keys:** `status`, `num_delete`, `walks`, `dlogz`, `maxiter`, `maxcall`, `final_delta_logz`, `acceptance`, `unmoved_fraction`, `scale`, `ncall_valid`, `x64`, `hops`, `hop_tries`, `hop_acceptance`, `mode_history`, `mode_tree` (`[label, parent label]` of every cluster made by a split), `folds`, `chunks`, `wall_time_s`, `compile_s`, `sampling_s`, `resumed`.
- **Checkpoints** (`tinyns/checkpoint.py`, format `tinyns-ckpt-6`: the state holds the cluster ids and their parents). One `.npz` file, written atomically at a chunk boundary at most every 10 minutes and at the end. A resumed run is bit-identical to an uninterrupted one (tested on CPU, x64 on and off), because each step splits the key it carries and the random stream depends on the step count only. A checkpoint with a different config, key, batch, x64 flag or float dtype is refused with a `ValueError`. A run stopped by `maxiter`, `maxcall` or `dlogz` continues under the new call's limits. The timings in `metadata` add up over sessions.
- **Batched runs.** `run(jax.random.split(key, B))` returns a list of `B` results. `step` is vmapped over the runs inside the loop, and a finished run is frozen while the others finish. With `batched_data=True` every array leaf of a pytree callable carries a leading axis of `B`. A batched run is not bit-identical to the run of its key alone (vmap changes XLA's summation order): in float64 they agree to roundoff, in float32 they agree in distribution.
- **Pytree callables.** The arrays of `jax.tree_util.Partial(fn, data)` (or any pytree callable) are arguments of the compiled kernels, so datasets of one shape share one compilation. Closure constants of 4096 elements or more are hoisted to arguments too. The kernel caches hold no data.
- **Precision.** x64 on and off are both supported and tested in CI.
- **Requirements.** Python 3.10+, `jax>=0.4.31`. CI runs the suite on `jax==0.4.31` too. On JAX before 0.4.38 the first `run` raised `NotImplementedError: Batching rule for 'optimization_barrier' not implemented`: tinyns now registers that rule itself there (`tinyns/_compat.py`). One barrier is left, on the hop's normal draw (without it the first run compiles 2 s longer at 10 and 13 dimensions and 3 to 4 s longer at 32, on an H100); the three others changed neither the compiled run nor the compilation and are gone, so fixed-seed results differ from the previous v1 in roundoff.

- **Sampling paths:** the Python kernel, the brute-force prior sampler, the isotropic proposal, ellipsoid bounds, the per-iteration loop, the rescue ladder and the affine cluster swap of v0.2.5 (replaced by the hop).

- **File formats:** checkpoints of every earlier format (`tinyns-checkpoint-npz-v1`, `tinyns-ckpt-2` to `-4`) and v0.x result files are refused.
- **Metadata:** the v0.x keys (`rwalk_*`, `replacement_*`, `cluster_*`, `jax_block_*`, ...) are replaced by the list above.
- **Repository:** `benchmarks/` (replaced by `bench/`), `tools/ab_bitwise.py` and its CI job, `RELEASE_CHECKLIST.md` (it described v0.1.0-alpha), and the v0.x examples (`banana_2d.py`, `constant.py`, `eggbox_2d.py`, `gaussian_1d.py`, `gaussian_2d.py`, `gaussian_2d_rwalk_jax_block.py`, `repeated_gaussian_evidence.py`, `save_load_result.py`), replaced by five: `quickstart.py`, `multimodal.py`, `checkpoint_resume.py`, `sbc_batched.py` and `functional_core.py`. ### Benchmarks

- **Head-to-head against tinyns 0.x, BlackJAX NSS, JAXNS, dynesty, UltraNest and Nautilus** on the 24 targets of `bench/` (20 or 40 seeds; GPU samplers on one H100, CPU samplers on 4 cores). The README has a compact table and `bench/RESULTS.md` every cell, the settings, the fairness caveats and the full validation gate at afa58dd (10 of 10 cases pass on the H100).
  - *At the competitors' settings* tinyns v1 is accurate on 18 of 24 targets at nlive 500 and on 22 at the default 1000. It fails on `rosen_d10` at 500 (logZ low by 0.22 ± 0.06), on the 32-D mixtures at 500 (minor mode lost in 25 to 30% of the runs) and on 5 of the 6 `sepM` cells; no competitor is accurate on any `sepM` target at its settings. With more live points (tinyns only) `sepM_d18` works at nlive 2000 and `sepM_d32` at 4000, where all 12 mixtures are accurate.
  - *Cost.* A compiled run takes 1 to 20 s and a first run 9 to 31 s (BlackJAX NSS: 9 to 77 s compiled; JAXNS: 16 to 360 s). tinyns does not need the fewest likelihood calls: Nautilus needs 1.7 to 24 times fewer, at an rms 2 to 28 times smaller, where it is accurate.
  - *Not like for like:* GPU and CPU wall times, Nautilus without a pool, UltraNest's MLFriends at d = 10, chain lengths at d >= 30, and tinyns's rows above nlive 500. `bench/RESULTS.md` lists these and the competitor cells that have not run. The tinyns rows were measured at afa58dd, one merge before the JAX 0.4.31 change, which differs only in roundoff.
- **`bench/summarize.py`** gains `--sha SAMPLER=SHA` (only the records written at one commit), `--reference-nlive`, the columns `sd`, `logzerr`, `run s` (wall minus compile) and `first s` (a cold start), a table of sampler versions and failures, and one accurate-cells row per `nlive`.

### Defaults

- **`nlive=1000` and `num_delete = nlive // 10` are confirmed by a sweep; no code change (v1 PR 5).** 362 cells of 40 batched runs on an H100 (x64): `nlive` 250 to 4000 times `num_delete / nlive` 0.05, 0.1, 0.25 and 0.5 on Gaussians (d = 2, 10, 18, 32, 64), the mixtures sepW, connW and sepM (d = 10, 18, 32), mix3_d10, rosen_d10, funnel_d10 and the eggbox, plus `num_delete=1` at `nlive` 500 on two targets and 85 single-run timing cells. The tables, data and scripts are archived outside the repository. The README section "Choosing `nlive` and `num_delete`" gives the guidance.
  - *`num_delete`.* `logzerr^2 * ncall` is the same at every share to 2%, and the measured scatter agrees (pooled `(logz - truth) / logzerr` has sd 0.92 to 1.09 on the Gaussians at `nlive >= 500` and 0.92 to 1.08 on the mixtures, at every share): accuracy per likelihood call does not depend on `num_delete`. The run time does (single run of gauss_d10 at `nlive` 1000: 1.14, 0.71, 0.54 and 0.28 s at shares 0.05, 0.1, 0.25 and 0.5; 26.8 s at `num_delete=1`). Shares above 0.1 are not the default because the diagnostics degrade there: the eggbox's scatter over `logzerr` is 1.52 to 2.47 at 0.25 and 0.5 (0.89 to 1.24 at 0.1, 0.82 to 1.16 at 0.05), sepM_d10 at `nlive` 1000 has a logit sd of 0.06, 0.07, 0.22 and 0.50 at the four shares, gauss_d64 at `nlive` 250 is 1.75 +- 0.16 high at 0.5, and the pooled insertion test rejects 5.1%, 6.1%, 13.2% and 29.7% of the runs at the 5% level (3600 runs per share). `num_delete=1` used 8% (gauss_d18) and 17% (sepW_d18) fewer calls than the default with a 2% smaller `logzerr`.
  - *`nlive`.* At 1000 every Gaussian is unbiased up to 64 dimensions (at 250, d = 32 and 64 are 0.17 to 0.44 high), rosen_d10 is at -0.05 +- 0.04 (-0.16 +- 0.05 at 500, -0.42 +- 0.11 at 250, +0.00 +- 0.02 at 2000) and the single-run time is nearly flat (gauss_d10: 0.54 to 0.85 s from 250 to 4000; gauss_d32: 2.7 to 4.2 s), while the calls are proportional to `nlive`. The 6% mode has no lost seed, a logit bias within 3 se and a logit sd of at most 0.4 from `nlive` 500 / 500 / 1000 (sepW) and 500 / 500 / 2000 (connW) at d = 10 / 18 / 32, and 1000 / 2000 / 4000 for sepM (one seed of 40 lost at d = 32); a logit sd of at most 0.1 needs 1000 / 1000 / 2000 for sepW. A rule such as `max(1000, 60 * ndim)` would fix d = 32 for this mode weight and double to quadruple the calls of every unimodal run above 16 dimensions, so the default stays 1000 and the README gives `5 * ndim / f` to `10 * ndim / f`.
  - *The unresolved flag misses most wrong weights.* The nine two-mode mixtures were run again at `num_delete = nlive // 10` with the `modes()` of 00176bb (36 cells of 40 runs; the same chains as the sweep at `nlive >= 1000`; `reflag.txt`). A run is wrong if its minor weight is lost or off by more than 0.4 in the logit: 178, 57, 16 and 1 of 360 runs at `nlive` 500, 1000, 2000 and 4000. `modes()` flags an unresolved mode in 24, 7, 4 and 0 of those, and 154 of 273, 50 of 223, 12 of 212 and 1 of 320 unflagged runs are wrong. All 95 runs that lost the mode report one mode and no warning: a lost mode leaves no label. At `nlive` 1000 the wrong runs are at d = 32 (49: connW 12, sepM 33, sepW 4) and sepM_d18 (8); `modes()` merges the connected modes of connW, so it never flags them. The README says that the absence of a flag is not proof and recommends a second run at twice the `nlive`.
  - *Eggbox.* The clustering holds one cluster through the whole run at `nlive >= 1000` and shares up to 0.1 (8 slots fill only at shares of 0.25 and above or at `nlive` 250, for 7 to 32% of the run), so the hop never acts and the slots are never full (`mode_slots_full` is 0 there); `modes()` now finds the peaks from the gaps between their live points and marks them `tracked: False` (at the sweep's sha, eb4631c, it reported one mode). logZ is unbiased (within 2 se at every `nlive` at share 0.1). The weights of the whole and half peaks are unbiased on average and scatter by 0.94, 0.68, 0.43 and 0.26 in the log at `nlive` 500 to 4000 (exact-draw floor 0.22 to 0.04); each 0.02 peak falls below 10% of its weight (the definition of lost in `bench/validate.py` and in the known limitations) in 32%, 15%, 4% and 0% of the runs, and some peak does in 78%, 35%, 8% and 0%; with a threshold of 0.1% of the weight, some peak is lost in 42%, 7%, 0% and 0% of the runs. The 0.08 peaks are never below 10% from `nlive` 1000.
  - *Memory.* Peak GPU memory of the 40-run batch: 0.3 GiB at d = 10 and 0.7 GiB at d = 32 with `nlive` 1000; 4.0 GiB at d = 64 with `nlive` 4000 (6.8 GiB at share 0.5).
  - *Lazy compaction* (skipping out-of-cube lanes at `num_delete > 1`) was not built: at the default share those lanes are 12 to 16% of the calls on the Gaussians, 19 to 23% on the mixtures and 6 to 8% on the funnel and Rosenbrock, the most it could save.

### Known limitations

- **Small modes.** A mode with fewer than about `5 * ndim` live points is not sampled reliably: its weight is biased or scatters widely, and the mode can be lost. A covariance-adapted walk needs that many points to learn a mode's shape. On one Gaussian with the shape of the 18-D bake-off target's minor mode, 1.7, 3.3 and 6.7 points per dimension left logZ 4.35, 0.21 and 0.03 too high. `modes()` flags such a mode `unresolved`; raise `nlive`.
- **More modes than the clustering separates.** The clustering has 8 slots and splits two ways, so it separates neither more than 8 modes nor modes on a lattice (an eggbox, where it never splits). The evidence is unaffected, but the hop does not balance such modes: on the eggbox at nlive 1000 the masses of the 0.08 and 0.04 modes scatter by 0.38 and 0.61 in logit over seeds, and a 0.02 mode was lost (a weight below 10% of the truth) in 15% of the runs (0.56, 1.5 and 32% at nlive 500). `modes()` marks them `tracked: False` and counts only those that planes across the axes of the unit cube separate; a mode with fewer than 8 live points stays merged with a neighbour.
- **Modes with thin arms or a funnel neck.** When a mode's contours are a core with thin arms or narrow into a neck (a scale parameter pressed against its prior edge and coupled to a location), the clustering cuts each mode into lumps and the hop's ellipsoids cover it poorly; the hop is then often off (its clusters are not eligible) or rarely accepted. On `needle_d18` the hop cut the run-to-run logit scatter of the minor mass from 0.57 to 0.19, against 0.37 to 0.019 for the same modes without arms; on `cauchy_d18` from 0.53 to 0.32; on an 18-D posterior with a funnel neck it gave no gain (0.25 over 3 runs, 0.30 for v0.2.5; hop acceptance 0.6%). logZ is unaffected (`needle_d18`: +0.03 +- 0.08, `cauchy_d18`: -0.09 +- 0.07 from the truth, 16 runs). `diagnostics()` warns, and `fold_sd / sqrt(3)` gives the scatter. On the 18-D posterior `modes()` also gave the minor mode 0.02 to 0.03 less mass than a cut on the physical parameter (the nearest-mode classification gives part of its tail to the wider main mode), and on `cauchy_d18` it merged the two modes into one in 2 of 16 runs, although the clustering had separated them.
- **Very small modes are not reported.** A cluster with at most `ndim` live points at its posterior median is not counted, and each of the three cross-fitted clusterings holds a third of a mode's points: with a 6% mode of 30 live points in 10-D (sepM_d10 at nlive 500), 32 of 64 runs reported one mode and no warning.
- **Curved targets are biased at small `nlive`.** At the default `walks` (60) and `num_delete = nlive // 10`, the logZ of the 10-D Rosenbrock is -0.42 +- 0.11, -0.16 +- 0.05, -0.05 +- 0.04, +0.00 +- 0.02 and +0.00 +- 0.02 from the truth at `nlive` 250, 500, 1000, 2000 and 4000, with a scatter of 1.64, 0.99, 1.08, 1.00 and 1.08 times `logzerr` (40 runs each, defaults sweep). The earlier advice (`walks` of 12 to 25 `* ndim`, a scatter of 2.3 times `logzerr` at the default) was measured before the seed-free covariance and the local walk and no longer holds. `bench/validate.py` still runs its Rosenbrock cases at `walks = 25 * ndim`.
- **Expensive likelihoods.** Parallel chains do not reduce the number of likelihood calls, and with `num_delete > 1` out-of-cube proposals are evaluated (`ncall` against `metadata["ncall_valid"]`). Use `num_delete=1` when one call already fills the device.
- **Cost of the mode tracking.** About 6% of the run time at 1 ms per likelihood call (H100, 40 batched runs; at most 18% over the validation cells). It is a fixed cost per step, so for likelihoods that take microseconds it is a larger share: 15 to 21% more per call on a 10-D two-mode target than on a 10-D Gaussian. Compilation takes about 10 s on a GPU.
- **float32.** Likelihood differences below about `1e-7 * |loglike|` are lost; enable x64 for large `|loglike|` or very narrow posteriors.
- **Insertion test.** With `num_delete > 1` the ranks of one step share their survivors, so the p-values are anti-conservative above `num_delete = nlive // 10`: 5%, 6%, 13% and 30% of correct runs fall below 0.05 at shares of 0.05, 0.1, 0.25 and 0.5 (see Defaults).
- **Compile cache.** A process keeps up to 8 compiled configurations per kernel; a loop over more configurations than that recompiles.
- **Bit-identical resume** is tested on CPU only.
- **A fixed seed is not bit-reproducible on a GPU in float32.** Five identical runs in separate processes gave four different `logz` (measured on `sepM_d32` on an H100 at afa58dd). On a CPU a fixed seed reproduces to the bit. The results agree in distribution.

## v0.2.5 (2026-10-02)

- **New default on the fast path**: `cluster_swap=True`. Mode weights of separated modes no longer drift with the seed when each mode is large enough. Replacement chains start from live points and cannot cross between separated modes, so each mode's live count did a random walk. On a real 18-D posterior with a 16% minor mode, two seeds gave 7% and 32%. tinyns now clusters the live points on the host between blocks and tracks the clusters across blocks. Once two clusters each have a volume share that predicts at least 2 x `ndim` live points, a tenth of the chain steps become an affine swap `u' = mu_b + L_b L_a^-1 (u - mu_a)` into another cluster's frame. The swap is accepted when `u'` is in the cube, above the threshold and nearest to frame `b`, with the Metropolis factor `det L_b / det L_a`. This is exact for any frames. The frame of the chain's seed is refit without the seed, and the rwalk keeps the global live covariance.
- Measured with tinyns on two-mode Gaussian targets with a 6% minor mode (nlive 500, 20 seeds per cell, swap off -> on). Logit seed scatter of the minor-mode mass: 0.46 -> 0.15 and 0.36 -> 0.10 at 4-D (two minor-mode shapes), 0.83 -> 0.16 at 10-D, 1.28 -> 0.39 at 18-D (200 seeds; the prototype gives 0.36 there). Mean mass with the swap on: 0.060, 0.060, 0.057 +/- 0.002 and 0.058 +/- 0.001. An eligibility threshold of 3 x `ndim` switched the swap off too early at 18-D (0.52, 40 seeds, one seed lost the mode). logZ bias and scatter are unchanged, and likelihood calls fell by 2% to 5%. A minor mode with fewer live points than about 2 x `ndim` (20 at 10-D, 36 at 18-D) gets no reliable benefit: the swap stays off or flickers, and the weights drift as before.
- On a real 18-D posterior (darksirens rung 5, BPL+2G, low-H0 mode holding 18-22% of the mass by a split-prior reference) at nlive 1000, 8 seeds per arm: the swap gives a low-H0 mass of 0.188 on average (logit sd 0.30) against 0.135 (logit sd 0.44) without it, and logZ -678.45 +/- 0.23 against the reference -678.3 +/- 0.2. At nlive 500 both arms come out near 0.08: the mode holds only about 28 live points (1.5 x `ndim`) when it is first detected, too few for the swap.
- A unimodal run that the clustering does not split is bit-identical to v0.2.4 for the same seed; a test pins fixed-seed fingerprints. On synthetic single ellipsoids, uniform boxes and the 13-D Gaussian there were no false splits. Real posteriors do get split sometimes: 3 of 10 seeds on a 13-D mock spectral-siren fit and 2 of 2 on another, none on a 16-D dark-siren fit. The move is exact either way, and those runs agree with v0.2.4 and the reference within `logzerr` (13-D means -58.578 vs -58.581, reference -58.623 +/- 0.029). The clustering runs on the host and never touches the PRNG stream. It costs about 12 ms per update at 13-D (one update every 128 iterations): 2.0 s of a 29 s run on a 13-D Gaussian.
- `result.metadata` reports `cluster_count_history` (`[iteration, clusters]` at each change), `cluster_swap_proposals`, `cluster_swap_accepts`, `cluster_min_population` and `cluster_modes`. `cluster_modes` gives, for each mode, its mass, its smallest live count between detection and its posterior median, and `urn_logit_sd`, the seed scatter of `logit(mass)` the drift would cause without the swap. Also `cluster_host_s`.
- `cluster_swap` applies to `sample="rwalk"`, `kernel="jax"`, `bound="none"`, `rwalk_proposal="live-cov"`, `replacement_chains=1` and `jax_block_size > 1`. Elsewhere it defaults to False, and an explicit `cluster_swap=True` raises `NotImplementedError`. Checkpoints record it and the cluster tracker's state. A checkpoint without the key reads as `cluster_swap=False`, so resume a v0.2.4 checkpoint with `cluster_swap=False`.

## v0.2.4 (2026-10-02)

- **Changed default**: `min_accepts=0` (was 1). A replacement chain that never moved is now kept as a copy of its seed, instead of being discarded and retried. The retry rule was biased: chains fail to move more often where the proposal fits poorly, so retrying under-sampled those regions. Measured with tinyns itself on two-mode Gaussian targets with a true 6% minor mode (nlive 500): at 4-D the old rule gave 2.9% +/- 0.3% and a logZ bias of +0.13 +/- 0.03, the new default 6.3% +/- 0.4% and +0.02 +/- 0.03 (40 seeds each); at 10-D, 1.7% +/- 0.6% against 6.7% +/- 1.7% (18 seeds each). Call counts are unchanged. A kept chain must still end inside the constraint, and an unmoved chain only counts if its seed is strictly above the threshold. Pass `min_accepts=1` for the old behaviour; checkpoints written with the old default need `min_accepts=1` to resume.

## v0.2.3 (2026-10-01)

- A loop over mock datasets no longer recompiles for every dataset. The fast-path kernel caches (block kernel, rwalk kernel and the initial live-point pass) were keyed on the identity of `loglike` and `prior_transform`, so each `jax.tree_util.Partial(loglike_fn, data_i)` built and compiled a new block kernel. They are now keyed on the callable's structure: a pytree callable's treedef and static leaves, with its array leaves passed as jit arguments, so JAX's jit cache keys the compiled program on their shapes and dtypes. On CPU, four `Partial` datasets of the same shape (1-D, 10k points, fixed `maxiter`) took 2 backend compiles for every new dataset in v0.2.2 (block kernel and live-point pass) and none in v0.2.3. Each result is bit-identical to a fresh run on that dataset. The live-point pass is now cached too; v0.2.2 compiled it again on every run, even for the same callable.
- Finished runs no longer keep their datasets alive. The `lru_cache(maxsize=32)` held up to 32 callables and so their data: in a four-dataset probe, v0.2.2 retained all four. The caches now hold no array leaves. Closures and plain functions are cached by identity through weak references, and their hoisted constants are dropped when the closure is garbage collected, so a dataset is freed once you drop it. Each closure object still compiles its own kernels; use a pytree callable to share one compile across datasets.
- Plain functions and small closures give bit-identical results to v0.2.2: a test pins fixed-seed `logz`, `samples`, `samples_u`, `logl` and `ncall` for the block and per-iteration paths. `Partial` and hoisted-closure runs were also checked to be bit-identical.
- `result.metadata` reports wall-time telemetry: `wall_time_s` (sampling wall time of the call), `compile_s` (time to the end of the first block, which carries the compiles) and `mean_ms_per_call` (wall time per likelihood call after the first block). Progress lines show `calls/s` since the first block, and callback states carry `calls_per_s`. There are no new arguments.
- The README notes that separate processes in a campaign can share compiles through JAX's persistent cache (`jax.config.update("jax_compilation_cache_dir", path)`). On CPU, a second process with a different dataset read its compiled programs from the cache and reached the end of its first block in 0.72 s instead of 1.62 s.

## v0.2.2 (2026-10-01)

- With the default single chain (`replacement_chains=1`), a live-cov proposal that leaves the unit cube no longer calls the likelihood. It is rejected either way, so it now takes a `lax.cond` branch that returns `-inf` without evaluating. `ncall` counts likelihood evaluations actually made; the acceptance rate and the batch bookkeeping use the proposal count. Samples and logZ are identical to v0.2.1; `logl` differs only at the 1e-13 rounding level, from XLA fusing the call inside the branch. Measured on an H100 against v0.2.1: a 13-D mock spectral-siren fit made 55% fewer calls (521k to 233k) and ran 1.8x faster (226 s to 124 s); a 1-D dark-siren fit made 12% fewer calls and ran 1.12x faster. With more than one chain, a `vmap`ped `cond` would evaluate both branches, so nothing is skipped.

## v0.2.1 (2026-09-30)

- On the fast path, closures now get the pytree-callable treatment automatically. A `loglike` or `prior_transform` without array leaves is traced once (`jax.make_jaxpr`), and every jaxpr constant with at least 4096 elements (a captured `jax.Array` or `np.ndarray`, including operands of a nested `jax.jit` call) is passed to the compiled kernels as a jit argument; smaller constants stay embedded. On a 1-D GW likelihood with 2.5M-row arrays (H100), the closure form took two backend compiles of 74 s and 78 s (first block after 172 s), and the pytree form 5.3 s and 6.8 s (first block after 23 s). With hoisting, the same closure reaches its first block after 21.6 s, the same as the pytree form (21.3 s). Through the darksirens ladder harness (a plain closure), a 1-D dark-siren run on the mock R1 fixture dropped from 861 s and 12.0 GB peak RSS to 387 s and 2.2 GB, against dynesty's 679 s. A 4-D real-data run dropped from 4.8 GB to 1.5 GB peak RSS. There is no API change. Closures with only small constants and plain functions are not traced into a new form and give bit-identical results to v0.2.0. A hoisted closure gives the same results as the equivalent `jax.tree_util.Partial`. If tracing fails, the callable keeps closure semantics and one debug-level log message is emitted per callable. Arrays captured inside the body of an inner `jax.jit` function stay embedded. Pytree callables remain the explicit form.
- `walks` now defaults to 12 in 1-D. In a 20-seed sweep, 1-D was unbiased from 10 walks (bias 0.2 x `logzerr`); from 2-D on, the default stays `max(25, 6 * ndim)`.

## v0.2.0 (2026-09-30)

- Added `rwalk_proposal="live-cov"`: each rwalk step is `step_scale * L @ z`, with `L` the Cholesky factor of the live-point covariance in the unit cube. Moves that leave the cube are rejected rather than reflected, and the step scale always adapts toward `rwalk_target_accept`. It is supported for unbounded `sample="rwalk"`, `kernel="jax"` with a fixed `replacement_chains`; other combinations raise `NotImplementedError`.
- **Changed defaults**: `NestedSampler(loglike, prior_transform, ndim).run(key)` and `run_static_nested` now run the fast path: `sample="rwalk"`, `kernel="jax"`, `rwalk_proposal="live-cov"`, `jax_block_size=32`, `walks=max(25, 6 * ndim)` and an initial `step_scale=0.5`. The old defaults were `sample="prior"`, `kernel="python"`, `rwalk_proposal="isotropic"`, `jax_block_size=1`, `walks=25` and `step_scale=0.1`; pass them explicitly to keep the old behavior. The default `kernel="jax"` needs JAX-traceable `loglike` and `prior_transform`.
- Where live-cov is unsupported (`kernel="python"`, a bound, or a `replacement_chain_schedule`), an unset `rwalk_proposal` falls back to `"isotropic"` with `step_scale=0.1` and `jax_block_size=1`, and `sample="prior"` defaults to `kernel="python"`. An explicit `rwalk_proposal="live-cov"` in those combinations still raises.
- Why: the fixed isotropic unit-cube step (`step_scale=0.1`) did not follow the contracting live set, so acceptance collapsed and the cost per iteration grew geometrically at d >= 4. On anisotropic correlated Gaussians, d = 2..18, live-cov keeps the likelihood calls per iteration flat at `walks`. Unbiased evidence needs `walks` of about 5-6 x `ndim`: `walks=25` biased logZ high by +0.5 nats at 13D and +1.4 nats at 18D, while `walks >= 5 * ndim` was within about 0.2 nats, with seed scatter matching the reported `logzerr`.
- With `kernel="jax"`, the initial live points are now evaluated in one compiled pass.
- `loglike` and `prior_transform` may be JAX pytree callables (`jax.tree_util.Partial(loglike_fn, data)`, an equinox-style Module, a registered dataclass with `__call__`). On the fast path (unbounded JAX rwalk: block kernel, per-iteration kernel, rescue draws and the initial live-point pass) their array leaves are passed to the compiled kernels as jit arguments instead of being embedded as constants. On a GW likelihood with 2.5M-row selection arrays (H100) this cut compile time from 76 s to 15 s and peak host RSS from 10.7 GB to 2.8 GB. Detection is automatic; plain functions and closures give bit-identical results to before. Bounded, fused-bounded and `replacement_chain_schedule` kernels keep closure semantics.
- Checkpoints record the resolved `walks`, `step_scale`, `rwalk_proposal` and `jax_block_size`, so a resume with default arguments matches a fresh run with default arguments. Checkpoints without `rwalk_proposal` are read as `"isotropic"` (no format-version bump).
- The benchmark and validation harnesses (`bench_static.py`, `overnight_jax_validation.py`, `validation/run_validation.py`) pin `rwalk_proposal="isotropic"` and `jax_block_size=1` unless a block size is requested, so their configurations are unchanged.

## v0.1.0-alpha

- Narrowed TinyNS public sampler surface to `sample="rwalk"` and `sample="prior"`.
- Removed legacy `slice`, `rslice`, and `sample="bound"` public sampler paths.
- Documented the recommended unbounded isotropic JAX rwalk fast path with `jax_block_size=32`.
- Added cached JAX block rwalk validation summaries and release checklist commands.
- Added optional B16/B32/B64/B128 block-size smoke documentation; B32 remains the default recommendation.
- Added a self-contained 10D GW-like stress-test template with diagnostic figures.
- Added or documented robust block-mode termination behavior for late replacement failures.
- Added a `logzerr` diagnostics breakdown and additional rwalk/replacement telemetry (`repl_ncall`, `repl_chains`, rescue/usage stage counts) to results and metadata.
- Added `NestedSamplingResult.logz_bootstrap(...)` (exported `LogZBootstrap`), a simulated-weights evidence-uncertainty estimator: it jitters the prior-volume shrinkages from their `Beta(nlive, 1)` law over the stored dead-point sequence and recomputes `logz` many times, returning the realization mean, standard deviation, and 16/50/84 percentiles. This captures the skewed prior-volume path uncertainty that the analytic `sqrt(H/nlive)` cannot. It is pure post-processing (no sampler changes) and does not capture sampling bias, so it is a lower bound on true single-run uncertainty when the constrained sampler is under-decorrelated (e.g. an inflated `insertion_rank_mean_z`).
- Added an experimental `rwalk_adaptive_step_scale` JAX-only rwalk option that adapts the isotropic proposal scale from constrained-replacement acceptance telemetry (default off, `step_scale=0.1` unchanged); the acceptance telemetry it adapts from was fixed to reflect true rwalk move acceptance rather than an earlier proxy.
- **Removed** `rwalk_proposal="live-cov"` and `rwalk_cov_jitter`: validation found concerning evidence pulls, and per-axis unit-cube reflection is not symmetry-preserving for correlated proposals. `rwalk_proposal` stays and now accepts only `"isotropic"`; passing anything else raises a clear removal error.
- **Removed** the `replacement_chain_schedule` + `jax_block_size > 1` combination: the in-JIT adaptive kernel evaluated all `max_chains` likelihoods at every stage regardless of schedule position, saving no compute while understating `ncall`/`chains_used` telemetry. Adaptive replacement-chain schedules remain supported at `jax_block_size=1` (the default).
- Fixed block-mode `ncall` undercounting failed-offset and rescue-ladder likelihood calls on an unrescued replacement failure; these are now always counted, matching per-iteration accounting.
- Fixed checkpoint cadence so `checkpoint_interval` is honored in block mode: checkpoints are now written on elapsed nested-iteration deltas rather than an exact-modulo check, so a large `jax_block_size` no longer skips the first several periodic saves (e.g. block 32 / interval 100 previously did not checkpoint before iteration 800).
- Fixed resume labeling: a resumed run that had already converged now reports `success=True, "converged"` instead of an incorrect `"maxiter reached"` message, and a resumed run at or past `maxiter` without convergence is labeled `"maxiter reached"` rather than defaulting to `"converged"`; fixed in both block and per-iteration modes.
- Persisted `effective_step_scale` in checkpoints as an optional `.npz` field (no checkpoint format-version bump; older checkpoints without the field still load) so adaptive step-scale state survives resume; added `rwalk_adaptive_step_scale`/`rwalk_target_accept` config validation on resume.
- Added a warning (not an error) when `NestedSampler` receives unknown keyword arguments; unknown kwargs are still stored, preserving dynesty drop-in compatibility.
- Validated `maxiter >= 1`; a fresh run with `maxiter=0` previously fell through and was mislabeled `"converged"`.
- Deduplicated run-loop state/bound-rebuild helpers, bound-rwalk JAX wrappers, and tuple-based ellipsoid-bound primitives; behavior-preserving, no public API change.
- Kept bounds, fused bounds, and larger block sizes experimental.

## Release caveats

TinyNS v0.1.0-alpha is intended as a small static nested sampler with a validated low-dimensional JAX rwalk fast path. High-dimensional, strongly curved, or multimodal targets require target-specific validation. The included 10D GW-like benchmark is a stress test for constrained-replacement mixing, not a production GW parameter-estimation pipeline.
